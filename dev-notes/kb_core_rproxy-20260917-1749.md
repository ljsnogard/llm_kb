## 0. 结论

| 子问题 | 结论 | 代价 |
| :--- | :--- | :--- |
| **stdio 告知端点文件名** | ✅ **可行，而且几乎没有阻力**：`kb_core` 现在的 **stdout 完全是空的**（实测 0 字节），加一行握手不会与任何现有输出冲突 | 约 10 行代码 + 一个"stdout 上有一行 JSON"的对外约定 |
| **`kb_core_rproxy` 中继 TCP ↔ IPC** | ⚠️ **架构上可行，但有前置改造**：`kb_svc_servo_ipc::Client` 目前**只有按域 trait 的方法**，没有"SEND 一个原始 `RequestEnvelope`、收一个 `ReplyEnvelope`"的入口。不补这个入口，代理只能转发已实现的那七个方法，连协议要求的 `Hello` 握手都转发不了 | 先给 `Client` 补一个低层信封接口（小）；其余是常规工程量 |
| **"远程访问者与 ipc 客户端同格式"** | ✅ 概念成立：`RequestEnvelope` / `ReplyEnvelope` 本来就是与传输无关的协议数据，换成"长度前缀 + postcard"的 TCP 帧即可，类型不用动 | 需要定一个 TCP 帧格式（postcard vs JSON） |

一句话：**思路成立，值得做；但要先补一个"裸信封"客户端接口，否则代理是残的。**

## 1. 现状核实（都是本轮实际跑/读出来的）

### 1.1 `kb_core` 的 stdout 是空的，日志走 stderr

```console
$ ./target/debug/kb-core --runtime-dir /tmp/kb-stdio/run --storage-dir /tmp/kb-stdio/data \
    >/tmp/kb-stdio/out.txt 2>/tmp/kb-stdio/err.txt
$ wc -c /tmp/kb-stdio/out.txt
0
$ cat /tmp/kb-stdio/err.txt
[2026-09-17T17:49:12Z INFO  kb_core::serve_] kb_core v0.1.0（协议 v1）
[2026-09-17T17:49:12Z INFO  kb_core::serve_] 运行时目录: /tmp/kb-stdio/run
[2026-09-17T17:49:12Z INFO  kb_core::serve_] 存储目录: /tmp/kb-stdio/data
[2026-09-17T17:49:12Z INFO  kb_core::serve_] IPC 端点文件: /tmp/kb-stdio/run/kb-20260917-2eec7df6d6a045ddb1cc96734fedb6b2.ipc
[2026-09-17T17:49:12Z INFO  kb_core::serve_] 已登记工作区: 0 个
[2026-09-17T17:49:12Z INFO  kb_core::serve_] 等待客户端连接（Ctrl-C 退出）
```

要点：

- 端点文件名的**信息已经有了**，但它是 `env_logger` 的一行格式化日志，
  在 **stderr** 上、带时间戳与模块名、受 `RUST_LOG` 影响。
  父进程要拿它就得解析日志——脆弱，不是握手。
- **stdout 一个字都没有** ⇒ 把握手放 stdout 是纯增量，不会破坏现有使用方式
  （管道、日志重定向都不受影响）。

### 1.2 `Client` 没有裸信封接口

`kb_svc_servo_ipc::Client` 的公开面只有：

```text
connect / connect_with_timeout        // 建连（含重试）
events()                              // 取事件流，只能取一次
+ TrWorkspaceService / TrSessionService 的七个方法（list/add/remove…）
```

内部的 `request_(&self, request: Request, cancel: C) -> Result<Reply, RpcError<ServoIpcError>>`
是**私有**的，`RequestEnvelope` / `ReplyEnvelope` 也没有对外出口。
所以一个"透明代理"没有可用的 API：它拿不到"发任意 `Request`、收任意 `Reply`"这一步。

### 1.3 服务端是**顺序**处理请求的

```rust
// connection_.rs::serve
while let Some(item) = requests.next().await {
    let envelope = item?;
    let reply = dispatch_(service, envelope.request).await;   // ← 处理完才读下一条
    self.reply_tx_.send(ReplyEnvelope::new(envelope.request_id, reply))?;
}
```

⇒ 一条 IPC 连接上的多个请求会**排队**（`request_id` 匹配仍然正确，
只是没有并行）。对代理来说：多路复用 N 个远程客户端是"能跑但不并行"，
等 `Ask`（长耗时）落地后会明显。

### 1.4 `Hello` 握手在服务端**还没实现**

`dispatch_` 只覆盖工作区与会话七个请求，其余一律回 `BadRequest`。
而协议规定客户端的第一条必须是 `Request::Hello`。
⇒ 今天的 `Client` 从不发 Hello（它只用那七个方法），所以没暴露问题；
但**远程客户端按协议发 Hello 会被拒**。这是代理落地前必须补的一块
（要么在服务端实现 `TrHandshake`，要么由代理自己应答 Hello）。

### 1.5 与进程/依赖有关的其它事实

| 事实 | 影响 |
| :--- | :--- |
| `kb_core` 只有 `[[bin]]`，**没有 lib target** | 代理没法在进程内起服务端；测试也没法直接复用它的模块 |
| 一个 crate **不能依赖另一个 crate 的 bin 产物** | rproxy 必须**被告知** `kb-core` 可执行文件的位置（见 §4.3） |
| 集成测试拿不到别的包的 `CARGO_BIN_EXE_kb-core` | 同上，rproxy 的端到端测试需要额外安排 |
| 工作区的 `compio` 只开了 `["fs","macros","time"]`，**没有 `net`**；且 `compio-net` **不在本机缓存里** | 想用 compio 写 TCP 要改 workspace feature 并联网拉一个 crate（网络可达） |
| `Client` 的字段是 `IpcSender`（Send+Sync）、`Arc<Mutex<HashMap<..oneshot::Sender..>>>`、`Mutex<Option<IpcReceiver>>`（`IpcReceiver` 是 Send 但 !Sync ⇒ 包进 `Mutex` 后 Sync）、`AtomicU64` | **`Client: Send + Sync`**，可以用 `Arc<Client>` 跨线程/跨任务共享（由字段类型推出，未加编译期断言） |
| 已有的发现机制：客户端在运行时目录里找内容非空的 `kb-*.ipc` | stdio 握手是**补充**而非替代：它解决"父进程启动子进程"这一场景的确定性，独立启动的客户端仍可扫描 |

## 2. 子问题一：stdio 握手

### 2.1 做法

`Listener::bind` 之后、进入 accept 循环之前，往 **stdout** 打一行机器可读的握手：

```json
{"event":"ipc_ready","ipc_name_file":"/run/user/1000/llm_kb/kb-20260917-2eec….ipc","pid":1234,"protocol_version":1}
```

- **一行一个 JSON 对象 + `\n` + flush**：父进程按行读，读到第一行合法握手就算就绪；
- 只承诺 **文件名**（客户端本来就要读文件内容，而内容要等 `accept` 才写，
  所以握手时它可以是空的——客户端已有重试）；
- 其余诊断继续走 stderr 日志，职责不混。

### 2.2 为什么可行

- stdout 现在是空的（§1.1），没有兼容包袱；
- 文件名在 `Listener::bind` 之后就是确定的，**不依赖 accept**，所以不会拖慢启动；
- 失败模式简单：父进程若在超时内读不到握手行，就当子进程启动失败。

### 2.3 需要拍板的点

1. **格式**：JSON（可扩展，`serde_json` 已是 kb_core 的依赖）还是 `KEY=VALUE`（更土但够用）；
2. **是否常开**：交互式跑 `kb-core` 时 stdout 会多一行。可选方案是加
   `--handshake=stdio|none`（默认 stdio），或只在被要求时输出；
3. **握手内容的边界**：只给文件名，还是顺带给 `endpoint`（ipc-channel 的端点名）、
   版本、pid？我倾向"文件名 + 版本 + pid"，端点名属于实现细节不写。

> 这属于对外约定（`AGENTS.md` 第 1 条），落地前要确认上面三点。

## 3. 子问题二：`kb_core_rproxy`

### 3.1 进程与数据流（MVP 形状）

```text
rproxy（父进程）                                   kb_core（子进程）
  │  spawn kb-core --runtime-dir R --storage-dir S
  │  ◄──── stdout 一行握手（含 ipc 文件名）
  │  Client::connect(R)                ← 复用已有客户端，含重试
  │  TcpListener::bind(127.0.0.1:PORT)
  │
  │  ◄── 远程客户端 N 条连接，帧 = [u32 长度][postcard RequestEnvelope]
  │  ── Client::request(envelope.request) ──► IPC 请求通道
  │  ◄── ReplyEnvelope ──► 按 request_id 写回"发起它的那条 TCP 连接"
  │  ◄── Client::events() ──► 广播给所有 TCP 连接
```

关键点：

- **一条 IPC 连接就够**：`Client` 内部的 `pending_` 表按 `request_id` 路由，
  天然把 N 个远程客户端的请求多路复用在一对通道上；
- **写回要按来源连接**：代理自己维护 `request_id → TCP 连接` 的映射；
- **事件扇出**：`Client::events()` 只能取一次，所以代理取一次、自己复制给各连接；
- **生命周期**：子进程退出 ⇒ 关闭所有 TCP 连接并退出；rproxy 退出 ⇒ 结束子进程。

### 3.2 必须先补的接口

在 `kb_svc_servo_ipc` 里放开一个低层入口（名字待定，形状与现有宏风格一致）：

```rust
impl Client {
    /// 发一个请求并等它的应答；`request_id` 由本方法生成。
    pub fn request<'f>(&'f self, request: Request) -> RequestAsync<'f, 'f>;

    /// 或者：保留调用方给的 `request_id`（代理转发原始信封时更自然）。
    pub fn send_envelope<'f>(&'f self, envelope: RequestEnvelope) -> SendEnvelopeAsync<'f, 'f>;
}
```

实现上是把现有的私有 `request_` 提上来定型 + 走一遍 `gen_mcf2`，属于小改动。
**不做这一步，代理就只能覆盖已实现的两个域，且无法转发 `Hello`。**

### 3.3 还需要补/决定的

| 项 | 说明 |
| :--- | :--- |
| 服务端 `Hello` | §1.4：要么实现 `TrHandshake`，要么由代理自己应答（后者会让"透明"打折扣） |
| TCP 帧格式 | 建议 `[u32 BE 长度][postcard bytes]`，载荷就是 `RequestEnvelope`/`ReplyEnvelope`/`Event`。理由：类型已有 postcard 往返测试、与 ipc-channel 内部编码一致、比 JSON 紧凑。备选：一行一个 JSON（便于 `nc` 手工调试） |
| 并发模型 | (a) `std::net` + 每连接一条线程 + `futures_lite::future::block_on` 驱动 `Client` 的 future（**不需要 compio，`Client` 的 future 是运行时无关的**）；(b) compio + `net` feature（要为 workspace 打开 feature 并拉 `compio-net`）。MVP 建议 (a)，与 kb_core 的一致性可以后补 |
| 背压 | ipc-channel 无界、TCP 有背压：每个连接要有**有界**发送队列，慢了就丢事件/断连接，不能无声涨内存 |
| 二进制定位 | rproxy 用 `--kb-core <路径>`，缺省在**自身可执行文件同目录**找 `kb-core`（`cargo build` 会把两者放进同一个 `target/debug`） |
| 测试 | 跨包拿不到 `CARGO_BIN_EXE_kb-core`。要给 rproxy 写端到端测试，建议**给 `kb_core` 加一个 lib target**（顺带支持"在进程内嵌入服务端"），或在测试里自行定位 target 目录 |
| 放置位置 | 按指示放 `kb_plugins/crates/`。但严格说它是**服务侧基础设施**而不是 LLM 插件，放 `kb_svc/crates/` 更贴切——这条请一并拍板 |

## 4. 与替代方案的比较

| 方案 | kb_core 的暴露面 | 额外进程 | 需要新写的 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| **`kb_core_rproxy`（本方案）** | 本机 IPC 不变 | 有（父进程 + 子进程） | 裸信封 API、TCP 帧、进程监管、事件扇出 | 远程访问与本地访问彻底分离；kb_core 保持"只服务本机" |
| **`kb_svc_socket`（`abs_kb_svc` README §7 已列为备选）** | kb_core 自己监听 TCP | 无 | 一份 `abs_kb_svc` 的 socket 实现 | 少一跳、少一个进程；代价是把网络面放进 kb_core，且"换传输"的抽象层本来就是为了这个 |
| **只用现有的 `kb-*.ipc` 扫描** | — | — | 无（已实现） | 只解决"本机客户端怎么找到端点"，不解决远程访问 |

也就是说：**本方案解决的是"跨机/跨容器访问"，而扫描解决的是"同机发现"**，
两者不冲突；而 `kb_svc_socket` 是同一目标下的另一种切法，值得在落地前一起比一次。

## 5. 风险与未决项

1. **安全性（本轮显式不考虑）**：TCP + 无鉴权 = 同网任何人可读写知识库。
   MVP 建议**只绑 `127.0.0.1`**，并在文档里把"无鉴权、无 TLS"写成硬性前提——
   要对外暴露必须先做鉴权，这不是"以后顺手加"的东西；
2. **服务端顺序处理**（§1.3）：代理下多客户端会互相排队；`Ask` 落地后要重新评估；
3. **唯一 accept 槽**：`kb_core` 一次只服务一个客户端，rproxy 占住之后，
   桌面客户端直连就得等它断开。要么"所有客户端都走 rproxy"，要么后续把 accept 改成并发；
4. **`Hello` 未实现**（§1.4）：远程客户端按协议握手会被拒；
5. **stdio 握手是新约定**：格式、是否常开、包含哪些字段都要拍板；
6. **crate 放置**（§3.3）与命名 `kb_core_rproxy` 的确认。

## 7. 已拍板的决定（2026-09-17 18:22）

这五条取代第 2/3/5 节里相应的"待定"表述。

### 7.1 握手分两个层面，作用都写进 `abs_kb_svc`

| 层面 | 谁跟谁握手 | 解决什么 | 格式由谁定 |
| :--- | :--- | :--- | :--- |
| **系统层（底层）** | 客户端进程 ↔ `kb_core` 进程 | **找得到、连得上**：内核端点在哪、怎么把连接建立起来 | **传输实现**（`kb_svc_servo_ipc` / `kb_core_rproxy`）；JSON 也好、`KEY=VALUE` 也好，不写进协议 |
| **应用层** | 客户端 ↔ `kb_core` 业务 | **谈得成**：双方是不是同一版本、服务端能不能干活、有哪些服务 | **`abs_kb_svc` 的协议**（`Request::Hello` → `Reply::Hello` → `Event::Ready`） |

- 应用层握手消息的格式**已经在 `abs_kb_svc::v1::desktop::handshake_` 里**，
  本轮只补"这两个层面各自负责什么"的说明，让 `kb_core_rproxy` 与后续客户端
  照着同一份公开协议执行；
- 系统层握手的消息格式**不进 `abs_kb_svc`**。

### 7.2 `kb_core_rproxy` 的职责与启动顺序

- 它**只负责启动** `kb_core` 并**记录 IPC 文件名**（通过 `--handshake-prompt=stdio`
  读到的那一行）；
- **不在启动时**跟 `kb_core` 做应用层握手；**等到有真实远程客户端连上来**才发起；
- stdio 通知**不是默认配置**：`--handshake-prompt` 的取值 `stdio | none`，
  **默认 `none`**。交互式跑 `kb-core` 时 stdout 保持干净。

### 7.3 传输与并发（先落地概念）

- `kb_core_rproxy` 是**应用层网关，但一次只服务一个客户端**；
- 运行时用 **compio**（工作区的 compio 需要打开 `net` feature；
  `compio-net` 已实测可以从 rsporxy 拉下来并编译通过）；
- **TCP 帧 = 长度前缀 + postcard**（`[u32 BE][postcard bytes]`，载荷是
  `RequestEnvelope` / `ReplyEnvelope` / `Event`）；调试便利性等有了真实客户端再说。

### 7.4 背压用 `buffex::circular_buff`

上下行各用一个有界环形缓冲：TCP 读 → ring → 转 IPC；IPC 应答/事件 → ring → TCP 写。
缓冲满时写入方等待，从而把背压一路传回对端，而不是无声涨内存。

### 7.5 放置与暴露范围

- 放在 **`kb_plugins/crates/kb_core_rproxy`**：它的定位就是**插件**，
  以后还会有别的 launcher、或者更高级的 rproxy，都往这里放；
- **不能只绑 localhost**：它存在的目的就是**局域网跨机测试**。
  因此"无鉴权、无 TLS"是**已知并接受的**临时状态，但同时意味着
  任何能访问到该端口的人都能操作知识库 —— 这条要写在 crate 文档与 README 的显眼位置，
  并且**一旦要用于非受信网络，鉴权必须先做**。

### 5.1 背压已接：上行有界环

```text
TCP 读半 ──► circular_buff（64 KiB 有界）──► 帧解码 ──► IPC ──► 应答 ──► TCP 写半
```

- **只做上行**：下行是严格的一问一答，攒不出队列；上行才是"对端可以拼命塞"的方向；
- 环满了写侧就等 ⇒ 读侧不再从 socket 取数据 ⇒ TCP 窗口关上 ⇒ 背压交给传输层。

**关于 `buffex::circular_buff` 的两条实测坑（值得写下来，因为它会影响任何用它的地方）**：

1. **只 drop 写端不等于 EOF**：必须显式 `Producer::close()`，否则读者永久停等；
2. **满环上已停等的写者，不会因为读端 `close()` 或 drop 而被释放**
   （`try_write_at` 只认 TX_CLOSED/空位，不认 RX_CLOSED）。
   ⇒ 网关的收尾约定因此是：转发侧无论因为什么收工，都先发一个**中止信号**，
   让读侧任务整体被丢弃（`ring_` + `main.rs::feed_uplink` 里都有注释），
   而不是指望环形缓冲自己解开。

实测：一个"声称 16 字节、只给 4 字节就断开"的客户端之后，网关照常服务下一个客户端
（日志：`远程客户端已连接 → 已断开`，紧接着下一个连上并跑通）。

### 还没做的（下一步）

1. **事件转发**：帧格式里种类位已经预留（`KIND_EVENT_`），但服务端还不推事件；
2. **并发**：一次一个远程客户端；要并发得先让 `kb_core` 能并发服务连接
   （现在是顺序 accept + 顺序处理请求），而且 `buffex` 的停等语义要再想清楚；
3. **鉴权**：见 §7.5，用到受信网络之外以前必须做；
4. **环的容量与压测**：64 KiB 是拍的，等有真实客户端再调。
