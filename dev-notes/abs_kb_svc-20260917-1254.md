## 0.1 本轮更新的两条澄清（2026-09-17 晚）

这两条澄清修正了本文件早先版本中的两处表述，**下面各章节已按此改写**：

### 澄清一：`abs_kb_svc` 的准确定义

> **`abs_kb_svc` 是知识库服务的业务通信抽象层**：定义各插件与 `kb_core` 通信的
> 抽象代码接口、通信内容，以及一个**与异步运行时无关的异步 RPC 业务接口**。

与早先版本的差别：早先把它描述为"跨进程通信抽象层"，范围偏窄且容易被误读为
"只关心传输"。准确的说法是——它同时负责 **通信内容**（业务数据）、
**抽象接口**（各插件如何调用 `kb_core`）与 **异步 RPC 形态**（运行时无关），
三者都属于"业务通信"的范畴，而**传输实现**才是它不负责的部分。

### 澄清二："零 serde" 不是目标

早先版本把"零 serde"当成一个选型约束，并据此推导出"零 serde 与 `String` 直发
不可兼得"的矛盾。**该约束作废**：

> "零 serde"只是在"以基于内存共享的 IPC 为前提"时才成立的目标。
> 该前提已经放弃（决策 1），因此"零 serde"**不再是一个有现实意义的约束**。

由此产生的三处修改：

| 早先表述 | 现在的处理 |
| :--- | :--- |
| §0 决策 4「暂不考虑 serde」 | **作废**（见 §2.4）：serde 只是数据类型的表示手段，不再是设计驱动 |
| §1.2 末尾"零 serde 与 `String` 直发不可兼得"的警告 | **删除**：这个矛盾是"零 serde"这个自设前提的产物，前提没了，矛盾也就不存在 |
| §5 决策项 1（α/β/γ 三选一） | **关闭**：直接用 typed 通道 + 派生（§5 已改为"已定"） |

§1.2 中"三选二"的分析**仍然有效**——它是对 *iceoryx2 为什么被放弃* 的论证，
与 serde 无关。

## 1. 对上一轮结论的修正

### 1.1 被修正的三点

| 上一轮的说法 | 修正后的说法 |
| :--- | :--- |
| 把载荷分成"路线 A 定长 typed / 路线 B serde 序列化字节"，并推荐 B | **框架错了**。既然走共享内存就是为了避免多余的编解码层，那么"用 serde 把业务类型序列化成字节再塞进共享内存"等于把共享内存当成一个普通的字节管道用，白白付了 `ZeroCopySend` 的全部约束却拿不到零拷贝的收益。这个方向不再讨论。 |
| 把"跨平台"当作一级选型约束，并因此担心 Android / iOS | **降级为背景信息**。`kb_core` 是独立 server，不迁移到移动端（决策 2）。 |
| 把 iceoryx2 的相对劣势主要归为"版本不稳 / 无访问控制" | **主因是"类型转换的强制成本"**。版本与安全问题仍然存在，但它们不是放弃它的决定性理由。 |

### 1.2 关于"必须有一轮类型转换"这一结论的裁定

团队提出的初步结论是：

> 基于内存共享的 IPC（包括 iceoryx2 等），无法不通过一轮"类型转换"等额外的工作、
> 以及在不侵入业务层代码设计的前提下，保证 `String` 等堆上内容能够轻易发送。

**裁定：基本正确，但需要把适用范围和成因说准。** 准确的表述是一个"三选二"约束：

> 在任意**跨地址空间**的 IPC 上，下面三条**至多同时成立两条**：
>
> 1. **零拷贝**：载荷不经过一次编解码/搬运；
> 2. **堆上内容直接发送**：`String` / `Vec` / `HashMap` 等无需改造即可发送；
> 3. **业务类型零侵入**：业务层类型不需要为通信做任何额外声明或改写。

**成因（逻辑链条）：**

```
① 进程 A 里 String 的缓冲区是一个「本进程虚拟地址」，在进程 B 里没有意义。
② 因此跨进程传递堆内容只有两种可能：
   (a) 把内容复制/编码到一块 B 也能看到的内存里，B 再解码 —— 放弃 (1)
   (b) 让类型自身只用「相对偏移」组织数据（无绝对指针、无堆分配），
       于是同一段内存在两个进程里都自洽 —— 代价是类型必须被改写成
       定长、无指针的形式；不做改写就得加一层镜像类型做转换
       —— 放弃 (2) 或放弃 (3)
③ 结论：不可能三条全占。
```

**iceoryx2 的选择与代价（实测印证）：**

- 它把 (1) 零拷贝当作不可让步的前提；
- 因此载荷必须实现 `unsafe trait ZeroCopySend`（自包含、无指针、`#[repr(C)]`、不实现 `Drop`）；
- 实测结果：`String` / `Vec<u8>` / `Option<u64>` / `serde_json::Value` 作为载荷**全部编译期失败**（`E0277`）；
- 所以它必然要放弃 (2) 或 (3)：要么业务类型重写为定长 POD（放弃 3），要么加一层镜像 POD 类型 + 双向转换（额外工作，且 `serde_json::Value` 这种任意形状根本无法表达）。

**ipc-channel 的选择与代价（本机实测）：**

- 它放弃 (1)：走 OS 原生消息通道（Unix socketpair / Mach port / 命名管道），
  类型经 serde 编解码；大载荷可选用 `IpcSharedMemory` 把内容放进共享内存只传句柄；
- 因此它保住了 (2)，并把 (3) 的侵入压到最低——**只需要一个 derive**，不改变类型的形状、
  不设容量上限、`String` / `Vec` / `Option` / 嵌套结构全部可以原样使用
  （实测跨进程 3 次往返 3.1 ms，含中文与 `Vec<u8>`）；
- 代价是：业务类型需要 `#[derive(Serialize, Deserialize)]`，且内容确实被复制/编码了一次。

⇒ 所以"堆上内容能否轻易发送"这件事，**不是共享内存的锅，而是"零拷贝"这个前提的锅**。
只要愿意放弃零拷贝，堆类型立刻就能直发；ipc-channel 就是这么做的。

> 早先版本在这里还写了一段"**零 serde** 与 `String` 直发不可兼得"的警告。
> 该警告已按 §0.1 澄清二删除：那是"以内存共享为前提"时自设的目标，
> 前提放弃后它不再构成约束。ipc-channel 的 `bytes_channel()` 依然存在、
> 依然可用，只是**我们不再需要为了"零 serde"而选它**。

## 2. 技术决策记录

### 2.1 放弃 iceoryx2（决策 1）

- 决定性理由：见 §1.2——它对"零拷贝"的坚持，把成本强制转嫁给了业务类型的形状。
- 次要理由（仍然成立，保留备查）：
  - 0.9.x 全部为 prerelease，每个 minor 都带 API Breaking Changes，1.0 未发布；
  - 没有任何访问控制，同 OS 用户下任意进程可读写；
  - 实测依赖规模 87 个 crate（同口径下 ipc-channel 为 41 个）。

### 2.2 `kb_core` 是独立 server，不考虑移动端（决策 2）

- `kb_core` 的部署形态是"一台机器上跑一个常驻服务进程"，客户端与插件连它。
- 因此上一轮文档 §3 的跨平台矩阵（Android IPC 被沙箱挡、iOS 无支持）**不再构成阻塞**。
- 这也顺带修正了一个隐含假设：共享内存 IPC 本来就**只能同机**，
  而"独立 server + 多客户端"的形态里，客户端可能来自别的机器——
  这个缺口在上一轮被"移动端"话题掩盖了，本轮显式记下（见 §5 决策项 4）。

### 2.3 通过替换 IPC 实现来适配其他端（决策 3）

- 将来若出现"客户端必须跑在别的平台/别的机器"的需求，
  正确做法是**换掉 `abs_kb_svc` 背后的实现**（进程内线程、socket、其他 RPC 框架），
  而不是要求共享内存方案去适配它。
- 这条决策直接定义了 `abs_kb_svc` 的存在理由：**它必须让传输实现可替换**。
  具体到 API 形状上，就是"业务语义 + 异步 RPC 接口在 `abs_kb_svc`，
  具体传输在另一个 crate"，见 §4。

### 2.4 ~~暂不考虑 serde（决策 4）~~ —— 已作废

**该决策作废**（§0.1 澄清二）："零 serde"只是"以内存共享的 IPC 为前提"时的目标，
前提已放弃，因此它不再构成约束。

现在对 serde 的立场是**中性的**：

- serde 只是"数据类型如何跨进程搬运"的一种手段，由实现 crate 的需要决定。
  `kb_svc_servo_ipc`（ipc-channel）的 typed 通道要求
  `T: Serialize + for<'de> Deserialize<'de>`，因此协议数据类型带
  `#[derive(Serialize, Deserialize)]`；
- 这**不改变类型的形状**：没有定长限制、没有容量上限、`String` / `Vec` / `Option`
  都能用——这正是选 ipc-channel 而不是 iceoryx2 的原因（§1.2）；
- `bytes_channel()` 依然存在，若将来某个方向确实不想引入 serde，可以局部使用它，
  但**不再把它当成全局目标**。

协议数据类型现在确实带 serde 派生，见
[`abs_kb_svc::v1::desktop/`](../kb_svc/crates/abs_kb_svc_v1_desktop/src/lib.rs)。

> **注意**：ipc-channel **不是共享内存中间件**，它是"跨进程的 Rust channel"。
> 共享内存只出现在 `IpcSharedMemory`（大载荷优化）这一处。
> 这一点必须写清楚，否则会与"把 IPC 改成基于共享内存"的原始目标产生理解偏差。

### 3.2 两条通道 + 一个共享内存类型

| API | 消息类型约束 | 用途 |
| :--- | :--- | :--- |
| `ipc::channel::<T>()` → `(IpcSender<T>, IpcReceiver<T>)` | `T: Serialize + for<'de> Deserialize<'de>` | 普通消息；`String`/`Vec`/结构体直发 |
| `ipc::bytes_channel()` → `(IpcBytesSender, IpcBytesReceiver)` | **无约束**（`send(&[u8])` / `recv() -> Vec<u8>`） | **完全不走 serde 的原始字节通路** |
| `IpcSharedMemory` | 自身实现 `Serialize`/`Deserialize`（crate 内置） | 大载荷放进共享内存，通道里只传句柄；`Deref<Target = [u8]>` |
| `IpcReceiverSet` | `add` / `add_opaque` / `select` / `try_select` / `try_select_timeout` | 一个线程多路复用多个通道 |
| `IpcOneShotServer<T>` | `new() -> (server, String)`；`accept(self) -> (IpcReceiver<T>, T)` | 进程间**引导握手**（名字是文件系统路径） |

`bytes_channel` 与 `IpcSharedMemory` 是两条**可选**的减负通路：
前者完全不经过序列化，后者让大载荷只传句柄。
按 §0.1 澄清二，它们不再承载"零 serde"这个全局目标，而是按需使用的工具。

### 3.3 本机实测结果（PoC：`external/ipc-channel-poc/`）

| 用例 | 结果 |
| :--- | :--- |
| 跨进程 typed 通道，收发含 `String` / `Vec<String>` / `Vec<u8>` 的结构体，3 次往返 | ✅ 3.1 ms；`echo:第 0 个问题：你好，知识库/4096` |
| 跨进程 `bytes_channel`，发 40 B / 64 KiB / **4 MiB** 三条 | ✅ 12.2 ms；服务端累计收到 4,259,880 字节 |
| 跨进程 `IpcSharedMemory` 传 4 MiB（消息类型零用户 serde） | ✅ 构建共享内存 66 ms、**发送句柄 486 µs**、服务端校验通过 |
| `IpcReceiver::to_stream()`（`async` feature）在 tokio 多线程下消费 500 条 | ✅ 11.8 ms，ticker 10/10 次未被饿死 |
| **反模式**：在异步任务里内联调用阻塞 `recv()` | ❌ 阻塞 300 ms 期间 ticker **0 次**（运行时被完全饿死） |
| **推荐做法**：同一场景改用 `to_stream().next().await` | ✅ 同样 300 ms 等待期间 ticker **26 次**（运行时保持响应） |

第 5、6 行是本轮最重要的实测：它把"阻塞 IO 必须离开异步执行线程"这句话从经验之谈变成了可复现的数字。

### 3.4 与 iceoryx2 的对比

| 维度 | iceoryx2 0.9.3 | ipc-channel 0.23.0 |
| :--- | :--- | :--- |
| 本质 | 共享内存零拷贝中间件 | 跨进程 channel（OS 消息通道 + 可选共享内存大载荷） |
| `String` / `Vec` 直发 | ❌ 编译期拒绝 | ✅ 直发（需 derive） |
| 零序列化通路 | ❌（必须 `ZeroCopySend`） | ✅ `bytes_channel()` / `IpcSharedMemory`（可选手段） |
| 零拷贝 | ✅ | ❌（`IpcSharedMemory` 仅省掉大载荷的复制） |
| 业务类型侵入 | 高（重写为定长 POD 或加镜像类型） | 低（一个 derive；用 bytes 通路则零侵入） |
| 版本稳定性 | 0.9.x 全 prerelease，minor 破坏性变更 | 0.23.0，2021 起持续演进，接口长期稳定 |
| 移动端 | Android 仅进程内、iOS 无 | iOS / Android 在自测平台列表内 |
| 依赖规模（本机同口径） | 87 crate | 41 crate |
| 异步支持 | 无 async API（roadmap 上） | **0.23 新增 `async` feature：`to_stream()`** |
| 引导方式 | 服务名（内部哈希成文件） | `IpcOneShotServer` + 名字（Unix 下是 socket 路径） |

### 3.5 ipc-channel 的关键限制（写进设计约束）

1. **一个 one-shot server 只接受一次连接**（官方 "Major missing features" 明说：
   "not suitable for implementing a system service"）。
   ⇒ `kb_core` 要服务多个客户端，必须自己设计引导/会合机制
   （每客户端一个 one-shot server、或一次 accept 后立刻重建并公布新名字）。
   这与现有 `plugin_socket` 的"父进程把路径喂给子进程"形态可以自然衔接。
2. **`send()` 永不阻塞，通道无界（unbounded）**（官方文档明说）。
   ⇒ 没有背压：消费方慢了，内存会无声增长。必须在 `abs_kb_svc` 的语义层
   自己限制 in-flight 请求数（见 §4.5）。
3. **`to_stream()` 只对 typed 通道提供**，`IpcBytesReceiver` **没有** stream 版本
   （0.23 源码 `asynch.rs` 里只 `impl<T> IpcReceiver<T>`）。
   ⇒ 由于 serde 已不再是被规避的目标（§0.1 澄清二），这不是问题：
   **直接使用 typed 通道**即可同时拿到"`String` 直发"与"开箱即用的异步"。
   `bytes_channel()` 保留为"确实不想序列化"时的局部手段。
4. **`to_stream()` 依赖一个进程级单例 router 线程**（源码里是 `LazyLock<Router>`），
   该线程持有 `IpcReceiverSet` 并阻塞在 `select()` 上；
   ⇒ 它同时是"阻塞被收敛到一处"的优点，和"单点故障"的风险。
5. `IpcReceiver` / `IpcBytesReceiver` 是 `Send` 但 **`!Sync`**；
   ⇒ 端点可以**移动**到 IO 线程，但不能跨线程共享引用。
6. 引导名字在 Unix 下是临时目录里的 socket 路径（实测形如
   `/tmp/.tmpXXXXXX/socket`，由 `tempfile` 生成、父目录 0700）
   ⇒ 访问边界同 OS 用户，与现有 UDS 0600 的模型一致。

## 4. `abs_kb_svc` 的异步 RPC 设计

### 4.1 问题陈述

> ipc-channel 本身不是异步的，且必然会导致 IO 线程进入 IO 等待。
> 这个问题该如何在 `abs_kb_svc` 中解决？

问题要拆成两半：

- **(甲) 契约问题**：`abs_kb_svc` 必须规定"实现方不许把阻塞调用放进返回的 future 里"，
  否则接口本身就会诱导实现者写出 §3.3 里那种饿死运行时的代码。
- **(乙) 机制问题**：阻塞调用被赶到哪里、结果怎么回到异步侧、取消怎么表达。
  `abs_kb_svc` 必须定义这个**交接形状**，但不依赖任何具体运行时。

### 4.2 方案对比与选定

| 方案 | 做法 | 评价 |
| :--- | :--- | :--- |
| A. 内联阻塞 | 在 async fn 里直接 `recv()` | ❌ 实测饿死运行时（ticker 0 次） |
| B. `spawn_blocking` | 用 tokio 的 `spawn_blocking` 包一层 | ❌ 把抽象层绑死在 tokio 上，违背"运行时无关"；且线程池有上限 |
| C. 每请求一条线程 | 每次 RPC 开一条 OS 线程做阻塞收发 | ❌ 线程数爆炸，`abs_kb_svc` 不该强制这种代价 |
| D. 复用 fd 做事件循环 | 把 ipc-channel 的 fd 接进 mio/tokio `AsyncFd` | ❌ ipc-channel 不暴露底层 fd；且会绑定到具体事件循环 |
| **E. 专用 IO 线程 + Waker 唤醒的完成量** | 每条端点（或每进程）一条 OS 线程持端点并阻塞在 `recv`/`select` 上；结果通过运行时可无关的完成量（`Waker` + oneshot）交回异步侧 | ✅ **选定**。运行时无关、线程数可控、取消可表达 |

方案 E 不是我们发明的：**ipc-channel 0.23 的 `to_stream()` 就是它的官方实现**
（单例 router 线程 + `IpcReceiverSet::select()` + `futures_channel::mpsc`），
而且 `futures_core::Stream` 本身与运行时无关，实测可以直接在 tokio 里 `.next().await`。
这给了我们一个"官方已经趟过一遍"的参照实现，也说明方案 E 的机制是可靠的。

### 4.3 `abs_kb_svc` 要定义的契约（对实现方的硬性要求）

1. **future 里禁止阻塞**：任何由 trait 返回的 future，其 `poll` 不得执行会阻塞
   OS 线程的操作（`recv`、`select`、文件 IO、锁等待……）。阻塞只能发生在
   实现方自有的 IO 线程上。
2. **IO 线程模型**：实现方必须为"阻塞端点"提供专用 OS 线程；
   线程与端点的对应关系、以及是否用 `IpcReceiverSet` 做多路复用，由实现方决定，
   但**不得**把端点直接暴露给调用者的执行器线程。
3. **完成量必须运行时可无关**：把结果从 IO 线程交回异步侧所用的原语
   只能是 `core::task::Waker` / `futures_core` 层面的东西，
   不得是 tokio / async-std / compio 的私有类型。
4. **唤醒不得丢失**：IO 线程先完成、异步侧后注册 `Waker` 的情形必须被正确处理
   （否则表现为"偶发卡死"）。这是方案 E 最常见的 bug。
5. **取消必须可达**：调用者丢弃 future 后，实现方要么向对端发出显式取消帧，
   要么依赖通道断开被对端感知；**不得**让对端永久阻塞等待。
6. **背压必须在语义层表达**：由于 ipc-channel 无界且 `send` 不阻塞（§3.5 第 2 条），
   `abs_kb_svc` 必须提供"同时最多 N 个未完成请求"这一类语义，
   而不是指望传输层兜底。

### 4.4 代码形状（对齐仓库当前的异步约定）

本仓库的异步抽象在 2026-09-17 的提交中已迁移到 **`abs_cancel` v0.2 + `gen_mcf2` +
`abs_async_iter`**，`abs_kb_svc` 必须按这套新约定写，而不是本文档早先引用的旧宏。

| 关注点 | 约定 | 来源 |
| :--- | :--- | :--- |
| 可取消的异步调用 | `abs_cancel::TrMayCancel`（v0.2） | `abs_llm` 依赖链 |
| 取消令牌 | `abs_cancel::TrCancellationToken`（含 `ChildToken` / `child_token` / `cancellation`） | 同上 |
| 生成 future 类型 | `gen_mcf2::gen_may_cancel_future` 属性宏 | 取代 `gen_mcf_macro` |
| 异步流（增量） | `abs_async_iter::TrAsyncIterator` | 逐项拉取，每项可取消 |
| 可订阅的流源 | `abs_async_iter::TrFlux` | `subscribe_async()` → `Iter<'f>: TrAsyncIterator` |
| 字符串抽象 | `abs_str::TrStringView` | 需要泛化字符串时使用 |
| 成功 / 失败 | `anylr::TrEitherOf` 或裸 `Result`（与所在模块保持一致） | `abs_llm` |
| 错误类型 | 实现 `core::error::Error` | `AGENTS.md` 第 9 条 |

**`gen_mcf2` 的用法约定**（摘自该 crate 的宏文档）：

1. 只能作用于 `async fn`；
2. 显式声明所需生命周期，且不要用 `__` 结尾的标识符（宏保留该后缀）；
3. 最后一个泛型**类型**参数是取消令牌类型，且在 where 子句中约束 `TrCancellationToken`；
4. 全部约束写在 where 子句里（不要内联在泛型参数上）；
5. 函数的最后一个参数必须是该取消令牌类型，且**按值**传入；
6. 宏参数里给出生成条目的名字前缀，并可放宽可见性：
   `#[gen_may_cancel_future(DoThing, pub)]`。

**为什么这套形状能解决 §4.1 的问题**：`TrMayCancel` / `TrAsyncIterator` 都是
`core` 层面的抽象，与执行器无关；而"阻塞在哪里发生"完全由实现 crate 决定
（例如 ipc-channel 的实现把阻塞收敛到它自己的 router 线程，再用
`futures_channel` 唤醒）。因此业务侧的 `await` 永远不阻塞执行器线程。

### 4.5 取消、背压与错误

- **取消**：沿用现有语义——`ask` 与 `cancel` 是两个独立操作，
  取消走显式帧（现有 `PluginRequest::Cancel { turn_id }` 已经是这个形状）；
  同时 future 被丢弃时的 Drop 语义要与显式取消一致，避免"界面已取消、服务端还在生成"。
- **背压**：由 `abs_kb_svc` 定义"同一会话同一时刻只允许一轮进行中"这类约束
  （现有 `hub.rs` 的 `active_turn` 就是这个语义），实现方只需忠实执行。
- **错误**：区分"传输层错误"（对端断开、编码失败）与"业务错误"（服务不存在、缺少 API key），
  前者属于 impl 的 `Err`，后者是正常应答里的一个分支——不要在类型上把两者混在一起。

### 4.6 已落地的数据定义

本轮已经把**桌面客户端这一侧**的通信内容落成代码：

| 位置 | 内容 |
| :--- | :--- |
| [`abs_kb_svc::v1`](../kb_svc/crates/abs_kb_svc/src/lib.rs) | 协议版本根；按"对端"分模块 |
| [`abs_kb_svc::v1::desktop/`](../kb_svc/crates/abs_kb_svc_v1_desktop/src/lib.rs) | 桌面客户端 × `kb_core`：15 个请求、11 个应答、9 个事件、6 个标识新类型；`mod.rs` + 11 个子模块 |

验证：`cargo test -p abs_kb_svc` ⇒ 23 个单元测试 + 9 个文档测试通过；`cargo clippy` 对本 crate 无告警。

本轮新增的三项决策：

1. **工作区与会话的标识由 `kb_core` 分配**（多端同步的权威来源），
   但客户端可以**本地先创建**、同步时再把临时标识换成服务端标识
   （协议用 `LocalId` 与 `WorkspaceId` / `SessionId` 两个不同**类型**来表达"尚未同步"）；
2. **表示形式的两条硬约束**：枚举用 serde 默认的**外部标签**、
   **不使用 `skip_serializing_if`**——因为目标传输的 postcard 不自描述
   （实测：内部标签与 `skip_serializing_if` 都会在**解码**时报错）；
3. **文件拆分原则**：只有需要内部共享逻辑 / 私有访问的代码才同处一个文件，
   目前只有 `ids`（共用一个私有宏）满足这一条。

插件侧（`v1::plugin`）与抽象的异步 RPC trait 尚未落地，是下一步。
