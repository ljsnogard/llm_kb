## 0. 本轮要解决的问题

会话目标：实践「通过 `kb_svc_servo_ipc` 向 `kb_core` 发请求、收应答」，
第一个功能实践是 **workspace 与 LLM 会话的增删查改**。

但当时的 `kb_core` 完全不具备这个地基：

| 现状 | 问题 |
| :--- | :--- |
| `main.rs` 只是 `kb_svc_salvo::launch::launch` 的薄壳 | HTTP / WebSocket 通道整体废弃，这个壳没有存在意义了 |
| 依赖 `kb_svc_salvo` 与 `tokio` | 前者在废弃之列；后者的运行时模型不适合承接 ipc-channel 的阻塞端点 |
| 没有任何工作区 / 会话的存储 | 「增删查改」连落点都没有 |
| README 以「它做了什么」开头 | 读者读完仍不知道怎么跑起来 |

所以本轮的顺序是：**先换地基**（去 salvo / tokio → 改 compio → 本地文件存储 →
命令行能真跑一遍增删查改），IPC 留到地基稳了之后再接。

## 1. 本轮拍板的四项决定

这四项都涉及对外约定（命令行参数、存储格式），按 `AGENTS.md` 第 1 条先在对话里
列出选项、由团队选定后才动手。

| # | 决定 | 选定 | 备选与被否的理由 |
| :--- | :--- | :--- | :--- |
| 1 | 命令行形态 | `--runtime-dir <目录>` + `--storage-dir <目录>` | 只留 `--runtime-dir` 更省事，但"运行时文件"与"数据文件"混在一处，将来清运行时目录会顺手删掉数据；保留 `--config` 也已无意义——它原本只服务于 salvo 的服务配置。 |
| 2 | 存储布局 | 按 id 分文件 + JSON：`workspaces/<id>.json`、`sessions/<workspace_id>/<session_id>.json` | 汇总索引 + 分文件会让"改一个会话"要写两个文件（索引 + 正文），多一处不一致的可能；JSONL 追加适合边生成边落盘，但单文件不再是合法 JSON，调试时要额外工具。 |
| 3 | 本轮范围 | 只做「去依赖 + compio + 本地存储 + README」，IPC 单独一轮 | `abs_kb_svc` 的 RPC trait 边界（其 README §10）尚未拍板，此时建 `kb_svc_servo_ipc` 会把未定的接口直接冻结进代码。 |
| 4 | `main` 行为 | 常驻骨架 **+** 一组临时 CRUD 子命令 | 只做常驻骨架公开面最小，但 README 要求"命令行优先、让用户先动手跑起来"，而骨架没有任何可交互的东西；只做自检后退出则与"服务进程"的定位不符。 |

其中第 4 项的临时代价是明确的：`src/cli_.rs` 与它的输出格式**不构成对外约定**，
IPC 接通后可以保留为维护命令，也可以整体删除。

## 2. 技术选择的因果链

### 2.1 为什么删掉 `kb_svc_salvo` 与 `tokio`

`kb_svc_salvo` 提供的是 HTTP + WebSocket 双监听器、仿 DSH 界面与插件 UDS 通道。
团队已决定进程间通信改走共享内存方向的 IPC（最终选定 servo/ipc-channel），
于是这套 socket / HTTP 通道整体作废。既然 `kb_core` 对 salvo 的依赖只是"借它的
`launch` 起进程"，那么删掉依赖之后 `kb_core` 必须**自己**成为那个进程。

连带删掉三个只为那套通道存在的入口：

- `tcp_addr` 位置参数：用户侧 HTTP 监听地址；
- `--config`：LLM 服务的 TOML 配置文件，属于 `kb_svc_salvo::settings`；
- `--assets-dir`：前端资源**覆盖目录**。前端资源本身在
  `kb_svc_salvo/src/web/assets/`，`kb_core` 不持有页面。

### 2.2 为什么是 compio，阻塞操作放哪

ipc-channel 不是异步 API；`abs_kb_svc-20260917-1254.md` §3.3 的本机实测给出了
一个量化结论：在异步任务里内联调用它的阻塞 `recv()`，会让 `current_thread`
运行时在 300 ms 内**一次定时任务都跑不到**；改用「专用 IO 线程 + Waker 完成量」
后同一场景能跑 **26 次**。

这条结论决定了运行时选型：业务侧需要一个能把阻塞收敛到别处的完成式运行时。
compio 满足这一点，且它的 `spawn_blocking` 正好安放"没有异步版本的系统调用"。

落到 `kb_core`：

| 位置 | 做法 |
| :--- | :--- |
| 入口 | `#[compio::main]`（`main` 返回 `ExitCode`，由宏生成的 `block_on` 承载） |
| 文件读写 | `compio::fs`（io_uring）：`read` / `write` / `rename` / `remove_file` / `create_dir_all` |
| 目录遍历、递归删除 | `compio::runtime::spawn_blocking` + `std::fs`——compio 0.19 的 `fs` 只提供单层 `remove_dir`，也**没有** `read_dir`（模块里连 `DirEntry` 类型都没有） |

也就是说，"改用 compio"不等于"所有 IO 都必须走 compio 的异步接口"；
**不许在 future 的 poll 里做阻塞调用**才是硬约束，`spawn_blocking` 是它的合法出口。

### 2.3 为什么存储直接复用协议类型

文件里存的就是 `abs_kb_svc::v1::desktop` 的 `Workspace` / `SessionDetail`
（后者含 `SessionSummary` + `Vec<Turn>`）的 JSON 表示。这样做的收益是
**存储格式与线上格式同源**：不会出现"某个字段能存进去、却发不出去"，
也不必为落盘再定义一套镜像结构。

同时，协议里两条约定直接变成了存储层的接口形状：

- **标识由 `kb_core` 分配** → `add_workspace` / `create_session` 内部调
  `WorkspaceId::generate()` / `SessionId::generate()`，返回值里带着新标识，
  供 IPC 层连同客户端的 `LocalId` 一起回传；
- **只发差异、不整棵树** → `list_sessions` 只读回摘要，正文必须走
  `get_session` 按需拉取。

### 2.4 为什么标识要校验、写入要用 rename

两条都是"存储层直接落在文件系统上"带来的具体风险，而不是通用洁癖：

1. **标识来自客户端，且协议明确说它是不透明字符串**（`ids_.rs`：
   "手工构造（例如测试里写 `"w-1"`）也完全允许"）。直接拿它拼路径就等于把
   `../` 穿越的机会交给对端。所以 `layout_::check_id_` 只放行
   ASCII 字母/数字/`-`/`_` 且不超过 128 字节，并在**拼路径之前**校验——
   有单元测试断言存储根目录之外不会出现文件。
2. **写入先落 `<名字>.json.tmp` 再 `rename`**：`rename` 在同一文件系统内原子，
   读者不会看到半个 JSON。进程被强杀时最坏留下一个 `.tmp`，
   而 `list_json_files_` 只认 `.json`，不会把它当成对象。

另外两条语义是刻意如此、并被测试钉住的：

- **`list_sessions` 对不存在的工作区报 `NotFound`，而不是返回空列表**：
  否则客户端把标识写错时，看到的是"这个工作区没有会话"，而不是"你指的这个地方
  不存在"；
- **删工作区级联删会话目录**：会话的归属字段就是 `workspace_id`，工作区没了，
  这些会话既列不出也读不出，留着只是垃圾。

### 2.5 为什么存储层的异步方法没有用 `gen_mcf2`

`AGENTS.md` 第 4 条要求"除非依赖链条上不存在 `gen_mcf2`"才可以用普通
`async fn`。本 crate 的依赖链上确实不存在它：根 `Cargo.toml` 里的 `abs_cancel`
至今没有任何成员引用，全仓库也没有 `gen_mcf2` / `gen_may_cancel_future` 的
使用点。因此在 `store_/mod.rs` 的模块文档里显式记下这条判定依据，
而不是默默省略。

将来 IPC 层引入取消语义时，这一层可以原样保留：文件操作本身足够短，
取消的价值在传输层（"对端永久阻塞"）而不在这里。

## 3. 落地位置

| 文件 | 内容 |
| :--- | :--- |
| `kb_svc/crates/kb_core/Cargo.toml` | 去 `kb_svc_salvo` / `tokio`；加 `abs_kb_svc` / `abs_llm` / `compio` / `serde` / `serde_json` / `thiserror`；dev 加 `tempfile` |
| `kb_svc/crates/kb_core/src/main.rs` | 入口：日志 → 解析 → 分发 → 退出码 |
| `kb_svc/crates/kb_core/src/args_.rs` | 命令行解析；`USAGE` 是用法的唯一来源 |
| `kb_svc/crates/kb_core/src/serve_.rs` | 常驻骨架（准备目录、打开存储、打印现状、`pending().await`） |
| `kb_svc/crates/kb_core/src/cli_.rs` | **临时**的 CRUD 子命令 |
| `kb_svc/crates/kb_core/src/store_/{mod,error_,layout_}.rs` | 本地文件存储：`Store`、`StoreError`、路径布局与标识校验 |
| `kb_svc/crates/kb_core/README.md` | 重写：命令行优先，设计说明在后 |

命名上按 `AGENTS.md` 第 5 条：私有 mod（`args_` / `cli_` / `serve_` / `store_` /
`error_` / `layout_` / `tests_`）、私有字段（`root_`、`values_`、`operands_`）、
私有函数（`parse_command_`、`resolve_paths_`、`write_json_` 等）一律加 `_` 结尾。
注意其中 `tests_` 与仓库既有 crate 的 `mod tests` 写法不同：第 5 条没有为测试模块
留例外，这里按字面执行；若团队认为测试模块应当沿用惯用的 `tests`，
改的只是一个模块名。

## 4. 验证

- `cargo test -p kb_core`：23 项全绿（13 项存储语义 + 8 项命令行解析 + 2 项布局）；
- `cargo clippy -p kb_core --all-targets`：无告警；
- 实机跑通完整一轮增删查改：新建工作区 → 建会话 → 列表 → 详情 → 改名 →
  删除会话 → 删除工作区，并确认删除工作区后 `sessions/<id>/` 目录一并消失；
- 实机确认常驻骨架会一直活着（`timeout -s INT 2` 才把它结束），
  参数错误以退出码 2 结束并打印用法。

## 5. 尚未决定 / 下一轮

1. **`kb_svc_servo_ipc` 的落地形状**：它依赖 `abs_kb_svc` 的 RPC trait 边界，
   而该边界（`abs_kb_svc/README.md` §10 第 1 项）还没拍板——是按业务域拆成多个
   小 trait，还是先只做"信道上收发 `RequestEnvelope` / `ReplyEnvelope`"。
2. **引导/会合机制**：ipc-channel 的一个 one-shot server 只能接受一次连接，
   `kb_core` 要服务多个客户端必须自己设计（每客户端一个 one-shot server，
   或 accept 后重建并公布新名字）。
3. **`StoreError` → 业务错误的映射表**：哪些算 `ErrorCode::NotFound`、
   哪些算 `ErrorCode::Internal`，需要在写请求处理时定下来。
4. **临时的 CRUD 子命令去留**：IPC 接通后是保留为维护入口，还是删除。
5. **存储换成 Turso 的时机**：本模块的边界就是为了这次替换而划的；
   替换前需要先明确 Turso 侧的 schema 与事务语义。
