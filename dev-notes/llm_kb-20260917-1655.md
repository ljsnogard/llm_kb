## 1. 仍在生效的技术决策

### 1.1 插件拆成两个 crate：`agent` 与 `adapt`

| crate | 位置 | 职责 |
| :--- | :--- | :--- |
| `kb_rig_llm_v1_agent` | `kb_plugins/crates/kb_rig_llm_v1_agent` | 用 rig 直接与**任意 rig 支持的 LLM 服务商**通信；自己保留完整对话上下文 |
| `kb_rig_llm_v1_adapt` | `kb_plugins/crates/kb_rig_llm_v1_adapt` | 把 rig 的原始数据转换成 `abs_llm::v1` 的数据；**具体载荷与线上表示主要由这里决定** |

分工的理由没变：插件只负责「说话」，主进程负责「翻译」。
变化的是"主进程"是谁——原来是 `kb_svc_salvo`，现在是 `kb_core`：

```text
kb_rig_llm_v1_agent  ──(原样 rig 数据)──►  IPC  ──►  kb_core
                                                        │
                                                        └─ 调用 kb_rig_llm_v1_adapt
                                                           （rig 数据 → abs_llm::v1）
```

> 插件侧与 `kb_core` 之间的消息类型（`abs_kb_svc::v1::plugin`）**尚未定义**；
> 上面这条"转换在主进程内"的分工是沿用下来的，等那份协议落地时需要再确认一次。

### 1.2 对话上下文归 agent 所有，但数据原样上报

`kb_rig_llm_v1_agent` **自己保留整个对话上下文**（多轮对话由它维护），
同时把**原样的 rig 数据**上报给主进程。

好处：agent 侧可以直接复用 rig 的多轮能力，而主进程不需要理解 rig 的上下文结构，
只需要把原始数据交给 `kb_rig_llm_v1_adapt` 转换。

### 1.3 跨进程复用的词汇统一用 `abs_llm::v1`

原来这条是针对"浏览器侧帧格式"写的（`kb_svc_salvo::wire`）。salvo 废弃后，
它以另一种形式活了下来：**协议数据直接复用 `abs_llm` 的语义类型**——
`abs_kb_svc::v1::desktop` 里的 `Turn.role` 就是 `abs_llm::v1::cont::Role`，
`TextDelta.logic` 就是 `LogicOutput`，不再镜像一套枚举。

因此"界面只应该看到统一抽象"这条目标仍然成立，只是承载它的不再是 `wire.rs`，
而是 `abs_kb_svc` 的协议类型。

### 1.4 `abs_llm` 临时引入 serde

**这是临时决策**：为了先把逻辑跑通，`abs_llm` 引入 `serde` 依赖，
并给少量纯数据 `enum` / `struct`（`Role`、`Capabilities`、`LogicOutput`、
`FinishReason`）派生 `Serialize` / `Deserialize`；`abs_llm` 保持 `no_std`，
serde 用 `default-features = false`。

**现状**：这条已经从"临时"变成了事实上的前提——`abs_kb_svc` 的协议类型要能在
ipc-channel（内部是 postcard）上跑，就必须有 serde 派生。真正需要处理
"缺省字段、rename、tag、原始 rig payload"的仍是 `kb_rig_llm_v1_adapt`。

### 1.5 依赖分层

- 多个成员共用的依赖写在根 `Cargo.toml` 的 `[workspace.dependencies]`；
- 只服务单个 crate 的依赖写在它自己的 `Cargo.toml` 里；
- 每个依赖用**标准表**（`[workspace.dependencies.<名字>]`）而不是内联表描述，
  便于 diff 与加注释。

细节见根 `Cargo.toml` 的注释。

## 3. 尚未决策的事项

按 `AGENTS.md` 第 1 条，涉及对外约定的变更必须先拍板：

1. **多会话**：协议已经用 `session_id` + `turn_id` 表达多会话，但"同一会话同时
   只允许一轮进行中"这类**背压语义由谁执行**（`kb_core` 还是插件侧）还没定；
2. **多 provider 的配置形态**：现在用 `provider` 字符串 + `base_url` + `model`
   描述一个 LLM 服务。rig 各 provider 的构造参数不同（有的要 `base_url`，
   有的要 region），是否需要 per-provider 的配置结构？
3. **跨机客户端**：是否显式承认"本地 IPC 只覆盖同机"，把跨机需求排除在近期范围外
   （若要支持，就该准备一个 `kb_svc_socket` 之类的网络实现）；
4. **`buffex` / `mm_ptr` 的定位**：`abs_kb_svc` 现在依赖这两个自研 crate
   （缓冲区交换与内存映射指针抽象），它们与"信道抽象"职责重叠，
   保留 / 替换 / 下沉尚未决定；
5. **`AddWorkspace` 的幂等**：客户端同步重发时如何避免重复创建
   （应由 `kb_core` 侧按 `LocalId` 幂等）；
6. **`RpcError` 是否需要第三个变体**：现在"用户主动取消"与"连接断了"都落在
   `Transport` 里，界面若要区分就得加变体；
7. **`kb_core/src/cli_.rs` 那组临时子命令的去留**：IPC 已经通了，它可以留作
   维护入口，也可以删。

## 4. 本机环境提示：Cargo 缓存是只读的

本机 `~/.cargo/registry` 与 `~/.cargo/git` 处于**只读文件系统**，`cargo fetch`
无法写入缓存，会以 `Read-only file system (os error 30)` 失败。工作区里因此
准备了一个可写缓存：

```bash
mkdir -p external/cargo-home
cp -r ~/.cargo/{registry,git} external/cargo-home/
cp ~/.cargo/config.toml external/cargo-home/
CARGO_HOME="$PWD/external/cargo-home" cargo test --workspace
```

`external/cargo-home` 只承载本机沙箱需要的 Cargo 缓存，不作为项目代码提交
（`.gitignore` 已忽略 `external/cargo-home/`）。

这条在引入 `ipc-channel` 之后更要紧了：它的 crate 不在默认只读缓存里，
不带 `CARGO_HOME` 直接构建会失败。

这属于本机沙箱限制，不是项目配置问题；正常开发机上无需这样处理。
