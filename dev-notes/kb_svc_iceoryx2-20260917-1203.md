## 0. 结论摘要

| 问题 | 结论 | 依据强度 |
| :--- | :--- | :--- |
| 用 iceoryx2 做 `kb_core` 与各子进程之间的进程间通信，技术上行不行？ | **行**。本机 Linux x86_64 上已经跑通跨进程 pub/sub、request/response、4 MiB 单次载荷、变长载荷、崩溃后再通信 | 本机实测（§10.1） |
| 大量数据（MB 级）的代码复杂度高不高？ | **不高，甚至比现有 WebSocket + JSON 略低**；真正的复杂度不在传输 API，而在 QoS 容量配置与样本借用生命周期 | 本机实测 + 官方 API 文档（§5） |
| 现有 `wire.rs` 那套 serde 类型能直接搬上共享内存吗？ | **不能**。`String` / `Vec` / `serde_json::Value` / `Option` 全部被 `ZeroCopySend` 拒绝，且是**编译期**拒绝 | 本机实测（§4.2） |
| 跨平台够不够？ | 桌面三平台（Linux / Windows / macOS）官方支持；**Android 只有进程内模式，IPC 被沙箱挡住；iOS 完全没有** | 官方 README + 官方开发文档（§3） |
| 是不是"全面删除 HTTP"之后唯一的通信方式？ | 只能覆盖**同机**通信。跨机（未来可能的移动端 / 远程客户端 / 隧道）没有答案 | 推断（§3.3） |
| 主要风险是什么？ | ① 版本还不稳（0.9.x 全是 prerelease，每个 minor 都有 breaking change，1.0 未发布）；② 完全没有访问控制，同用户任意进程都能读写（涉及 API key）；③ 移动端不可用 | 官方 README / FAQ / roadmap（§8） |

**一句话**：把 socket 换成共享内存这件事，**技术上成立、时机上很划算**，但它会把三个原本被 HTTP/socket 掩盖的问题顶到台面上——载荷类型必须重新设计、进程拓扑必须重新设计、安全模型必须重新设计。这三件事才是这次重构的真实工作量，而不是"把 `TcpListener` 换成 `Node::new()`"。

## 1. 研究范围与方法

### 1.1 要回答的三个问题（来自需求）

1. **跨平台考虑**：`kb_core` 与 `kb_admin_desktop` 未来要跑的平台上，iceoryx2 是否可用、是否有暗坑。
2. **复杂数据适用性**：现有 `abs_llm::v1` / `wire.rs` 里的语义类型，能不能直接作为共享内存载荷。
3. **大量数据通信的代码复杂度**：MB 级数据（知识库检索结果、长文本、附件）走共享内存要写多少代码、有哪些坑。

### 1.2 证据分级

本文所有结论都标注来源，分三档：

- **【实测】**：本机（Linux x86_64，`uname` 见 §10.1）用 iceoryx2 **0.9.3** 真跑出来的结果，PoC 源码在 `external/iceoryx2-poc/`。
- **【官方】**：iceoryx2 官方 README / FAQ / Book / release notes / docs.rs 或 crates.io 元数据。
- **【推断】**：由前两者推导，文中显式标注"推断"。

**没有**把"官方说支持"当成"我们这儿能用"——凡是能实测的都实测了。

- 【官方】**0.10 不存在**，**1.0 也不存在**（crates.io 查询 `0.10.0` / `1.0.0` 均为 404，GitHub tag 止于 `v0.9.3`）。
- 【官方】v0.9.0 发布公告称："计划在 iceoryx classic 生命周期结束（今年年底）之前发布 iceoryx2 v1.0"。即 **1.0 是计划，不是现状**。
- 【官方】四个 v0.9 的 GitHub release 全部带 `prerelease: true` 标记；crates.io 侧 `max_stable_version` 仍为 0.9.3。
- 【官方】MSRV 1.85，edition 2024（0.8.x 还是 MSRV 1.83 / edition 2021，再往前是 2021）。
- 【官方】licence：`MIT OR Apache-2.0`。

**与本仓库的兼容性**：本仓库 `rust-toolchain.toml` 锁定 nightly（`abs_llm` 用了 `#![feature(try_trait_v2)]`），实测工具链 `rustc 1.100.0-nightly`，workspace 所有成员 `edition = "2024"`。iceoryx2 0.9.3 的 MSRV 与 edition 要求**都能满足**，实测编译通过【实测】。

### 2.2 命名 / API 纠正（照着旧资料写代码会踩的坑）

| 常见说法（旧版本或过时 FAQ） | 0.9.3 的真实情况 |
| :--- | :--- |
| `FixedSizeVec` / `FixedSizeByteString` | 0.8.0 起改名为 **`StaticVec<T, CAP>` / `StaticString<CAP>`**；v0.9.3 的 FAQ 自己还写着旧名字（FAQ 陈旧） |
| `send_slice` / `receive_slice` / `send_custom_payload` | **都不存在**。对应物是 `loan_slice` / `loan_slice_uninit` + `write_from_fn` / `write_from_slice`，以及 `Subscriber<Service, [T], _>::receive` |
| `PlacementNew` | 名字是 **`PlacementDefault`**（trait + derive） |
| `max_slice_len`（服务级） | 不存在。切片容量在 **publisher** 上配：`.initial_max_slice_len(n)` |
| `global.max_shm_size`（配置项） | **不存在**。段大小由 QoS 最坏情况推导 |

### 2.3 版本风险（重要）

- 【官方】0.5 / 0.6 / 0.7 / 0.8 / 0.9 **每个 minor 的 release notes 里都有一节叫 "API Breaking Changes"**。所以 `0.9 -> 0.10` 必须当作破坏性升级处理。
- 【官方】unreleased 分支已经又把 MSRV 抬到 1.89，并且**删除了 `Listener::{try,timed,blocking}_wait_one`**（改名/改签名）。也就是说 0.9.3 上的代码在下一个 minor 几乎肯定要改。
- 【官方】"Currently, iceoryx2 does not provide an async API but it is on our roadmap"（issue #47）。**没有 async API**，只有同步的 `receive()` / `WaitSet`。

**⇒ 结论**：可以用，但应当把 iceoryx2 的使用**收敛在 `kb_svc_iceoryx2` 一个 crate 内**（正好也是需求里给的模块分工），让升级只影响一层。

## 3. 跨平台

### 3.1 官方支持矩阵

【官方】v0.9.3 README 的平台表（tier 1 = 安全/安全特性全开；tier 2 = 特性受限；tier 3 = CI 不测）：

| 平台 | 状态 | 当前 tier | 目标 tier |
| :--- | :--- | :--- | :--- |
| Linux x86_64 / aarch64 / 32-bit | done | 2 | 1 |
| Windows | done | 2 | 2 |
| macOS | done | 2 | 2 |
| FreeBSD | done | 2 | 1 |
| QNX 7.1 / 8.0 | done | 3 | 1 |
| **Android** | **proof-of-concept** | — | 1 |
| Bare Metal（`no_std`） | proof-of-concept | — | 1 |
| VxWorks | proof-of-concept（ekxide 分支） | — | 1 |
| **iOS** | **planned** | — | 2 |
| FreeRTOS / ThreadX / RTEMS / Redox / watchOS | planned | — | 2 |

【官方】CI 实际覆盖：`ubuntu-latest`、`macos-latest`、`windows-latest`、`ubuntu-24.04-arm`。

【官方】Book 的说法与之呼应：**"out-of-the-box" 的平台是 Linux、FreeBSD、macOS、QNX、Windows**；要加别的平台得自己实现 PAL（platform abstraction layer）并**长期维护**——通过 `IOX2_CUSTOM_PLATFORM_CONFIGURATION_PATH` / `IOX2_CUSTOM_POSIX_PLATFORM_PATH` 两个环境变量替换编译期设置与 POSIX 实现。

### 3.2 三个致命细节

**Android：IPC 被沙箱挡死。**
【官方】README 脚注："A proof-of-concept for Android platform support is available. Currently only local, inter-thread communication works."；开发文档更进一步："The MVP work only with the `local` and `local_threadsafe` service variant. The `ipc` and `ipc_threadsafe` service variants need more work to circumvent the Android sandbox limitations."

⇒ 也就是说 `ipc::Service` / `ipc_threadsafe::Service`（本方案要用的两个）在 Android 上**根本不能用**。这直接决定：**若 kb_core 跑在 Android 上、客户端 App 通过共享内存连它，做不了。**

**iOS：不存在。** 状态是 "planned"，v0.9.3 源码树里没有任何 iOS 相关文档或实现。
【推断】具体阻塞点（App Sandbox、无 `/dev/shm`、`shm_open` 限制）官方没有写，但结论明确：不可用。

**macOS：官方说 done/tier 2，但代码里有明确的妥协。**
【官方】0.9.3 源码事实：

- macOS 走通用 POSIX 分支，**`SHARED_MEMORY_DIRECTORY = "/dev/shm/"`**——而 macOS 原生没有 `/dev/shm`。
- `shm_open` 被**模拟**实现：逻辑名 → 生成唯一名，用一个状态文件（`<TEMP_DIRECTORY>/*.shm_state`）持久化映射关系。
- **共享内存权限在 macOS 上无法设置**：`shm_open` 忽略调用方 mode 强制 `S_IRWXU`，`fchmod` 吞掉 `EINVAL` 却报告成功（都标着 `TODO iox2-156`）。
- `AT_LEAST_TIMING_VARIANCE = 1.0`（其他平台 0.25），即官方自己承认 macOS 时序抖动更大。
- unreleased 分支上有多个 macOS 修复（`fchmod`/`shm_open` workaround、`pthread_create` race、`CLOCK_MONOTONIC` 常量错误）。

⇒ macOS **能用**（同机、同用户），但它是这套方案里"最薄"的一块；升级 iceoryx2 时优先在 macOS 上回归。

### 3.3 对 `kb_admin_desktop` 的影响（需要拍板）

`kb_admin_desktop` 是 Flutter 工程，脚手架里带着 Android / iOS / macOS / Linux / Windows 全套目标（`kb_clients/kb_admin_desktop/{android,ios,macos,linux,windows}`），但**现在还没有接任何传输层**——代码注释明说"下一阶段将通过 `ws://<host>/ws/chat` 连接"【实测读码】。

共享内存 IPC 有一个硬前提：**通信双方必须在同一台机器上**。于是：

| 场景 | 结论 |
| :--- | :--- |
| 桌面客户端（Linux/Windows/macOS）连本机 `kb_core` | ✅ 可行 |
| 移动端 App 连**本机**`kb_core`（kb_core 也跑在手机上） | ❌ Android 不行（IPC 被沙箱挡），iOS 不行（无支持） |
| 移动端 App 通过共享内存连**另一台机器**的 `kb_core` | ❌ 语义上不成立（共享内存不跨机） |

【推断】**"全面删除 HTTP"等价于"放弃移动端 + 放弃远程客户端"**，除非另开一条跨机通道（iceoryx2 有 gateway/tunnel 概念，但那是把共享内存桥接到网络，仍然是额外的一层，且 0.9.x 里 tunnel 相关 crate 正在改名/重构）。

这一条必须由团队确认：`kb_clients/kb_flutter`（目前是空目录）与 `kb_admin_desktop` 的 android/ios 目标，是否就此放弃或推迟。

## 4. 复杂数据适用性

### 4.1 硬约束：`ZeroCopySend`

【官方】0.9.3 里 `ZeroCopySend` 是 **`pub unsafe trait`**，derive 宏要求结构体带 `#[repr(C)]` 且所有字段都实现该 trait。官方 Safety 文本：

> the types are self-contained, meaning they shall not contain pointers, references, indices or handles to resources that are not part of the type.
> the types must have a uniform memory representation, meaning they are annotated with `#[repr(C)]`.
> The type and all of its members shall not implement `Drop`. The sender always owns the data and is responsible to cleanup everything.

FAQ 的 SEGFAULT 一节说得更直白：

> This is because shared memory is mapped at different offsets in each process, rendering absolute pointers invalid. Additionally, if the data structure uses the heap, it is stored locally within a process and cannot be accessed by other processes. As a result, data types such as **`String`, `Vec`, or `HashMap` cannot be used as payload types**.

### 4.2 实测结果表

PoC 里对每个类型都做了"正向能不能编译 / 反向报什么错"的验证：

| 载荷类型 | 结果 | 编译期错误（实测原文） |
| :--- | :--- | :--- |
| `u64`、`[u8; N]`、`f64` 等 POD | ✅ 通过 | — |
| `#[repr(C)] struct` 含定长数组（本 PoC 的 `TurnChunk` / `Command` / `Reply`） | ✅ 通过 | — |
| **`#[repr(C)] enum`**（含带字段变体） | ✅ **通过**（`#[derive(Debug, Clone, Copy, ZeroCopySend)]`） | — |
| `String` | ❌ | `error[E0277]: the trait bound String: ZeroCopySend is not satisfied` |
| `Vec<u8>` | ❌ | `error[E0277]: the trait bound Vec<u8>: ZeroCopySend is not satisfied` |
| `#[repr(C)] struct { turn_id: String, text: String }` | ❌ | `error[E0277]: the trait bound String: ZeroCopySend is not satisfied`，且 **"this error originates in the derive macro `ZeroCopySend`"** |
| **`Option<u64>`**（即 `wire::Usage` 那三个可选计数） | ❌ | `error[E0277]: the trait bound Option<u64>: ZeroCopySend is not satisfied` |

关于 `Option`：【官方】0.9.0 起**故意**移除了 `Option` / `Duration` 的 `ZeroCopySend` 实现（bugfix #1312），官方公告理由：

> Rust's standard `Option` and `Duration` types are not suitable for shared memory because their layout is not guaranteed to be ABI-stable. We added shared-memory-compatible alternatives that implement `ZeroCopySend` and can safely be used in payloads.

替代品是 **`RelocatableOption<T>` / `RelocatableDuration`**（在 prelude 里）。
【推断】这意味着 `Usage { input_tokens: Option<u64>, ... }` 这种很自然的表达，必须改写成"哨兵值"或 `RelocatableOption`。

### 4.3 与现有类型的逐项对照

现有 `kb_svc_salvo/src/wire.rs` 与 `kb_rig_llm_v1_agent/src/protocol.rs` 的字段，逐个对照 `ZeroCopySend` 要求：

| 现有写法 | 能否直接上共享内存 | 处理方式 |
| :--- | :--- | :--- |
| `turn_id: String` | ❌ | 定长 `[u8; 36]` + 长度，或 `StaticString<N>` |
| `text: String` / `message: String` / `arguments: String` | ❌ | `StaticString<N>`（容量必须预先拍板）或走字节载荷 |
| `services: Vec<String>` / `providers: Vec<String>` | ❌ | `StaticVec<StaticString<N>, M>` 或序列化 |
| `Option<String>` / `Option<u64>` | ❌ | `RelocatableOption<T>` |
| `serde_json::Value`（`PluginEvent::Raw.payload`） | ❌ | **无法用定长类型表达**，只能序列化成字节 |
| `#[serde(tag = "type")] enum` | ❌（带 `String` 字段时） | 定长 tag + 联合体式结构体；实测纯 `#[repr(C)] enum` 本身可用 |
| `Capabilities { bool × 4 }` | ✅ | 直接可用 |
| `FinishReason` / `LogicOutput` / `ErrorCode`（unit-only enum） | ✅ | 直接可用（实测 `#[repr(C)] enum` 通过） |

### 4.4 类型身份：跨进程必须是"同一个类型"

【官方】载荷的跨进程识别靠 `ZeroCopySend::type_name()`（默认是 `core::any::type_name::<Self>()`，即含 crate 路径）。类型定义如果分别出现在两个二进制 crate 里，会被判为不兼容（FAQ 的 `IncompatibleTypes`）。

⇒ **载荷类型必须放在双方共同依赖的 crate 里**（这正是 `abs_kb_svc` 的定位），并且要保证版本一致。
【官方】逃生口：`#[derive(ZeroCopySend)] #[type_name("llm_kb::TurnChunk")]` 可以手工固定类型名，从而解耦 crate 路径/版本。

### 4.5 可变长容器的额外依赖

【官方】`StaticVec` / `StaticString` 等**不在 `iceoryx2` 的 prelude 里重新导出**（prelude 只从 `iceoryx2-bb-container` 引了 `SemanticString`）。要用它们必须**额外直接依赖 `iceoryx2-bb-container`**，并且版本必须与 `iceoryx2` 严格同步（否则 `ZeroCopySend` 会解析到不同版本的 trait，连接直接失败）。

【推断】这给 `abs_kb_svc` 带来一个现实约束：**如果 `abs_kb_svc` 要定义带 `StaticString` 的载荷类型，它就必须依赖 iceoryx2 的容器 crate**——这跟"插件只必选 `abs_kb_svc`、可选 `kb_svc_iceoryx2`"的目标产生张力，详见 §6.8。

## 5. 大量数据与代码复杂度

### 5.1 三条可选路线

| 路线 | 载荷类型 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| **A. 定长 typed** | `#[repr(C)] struct` + `StaticVec`/`StaticString` | 真零拷贝；跨语言布局兼容 | 所有字段要重写成定长；容量必须预先拍板；`serde_json::Value` 无法表达 |
| **B. 字节切片** | `publish_subscribe::<[u8]>()` + `serde` 序列化 | 语义类型完全不动；代码量与现状持平 | 失去"typed 零拷贝"，只剩"单次序列化 + 免内核拷贝" |
| **C. 混合** | 控制/状态帧用 A，内容帧用 B | 兼顾 | 需要两套约定，得管住边界 |

### 5.2 代码复杂度实测（路线 B）

发布 4 MiB：

```rust
let service = node.service_builder(&SERVICE.try_into()?)
    .publish_subscribe::<[u8]>()
    .max_publishers(1).max_subscribers(1)
    .subscriber_max_buffer_size(1).history_size(1)
    .open_or_create()?;

let publisher = service.publisher_builder()
    .initial_max_slice_len(BIG_CAP)                     // 关键：不设就租不到大切片
    .allocation_strategy(AllocationStrategy::PowerOfTwo)
    .create()?;

let sample = publisher.loan_slice_uninit(BIG_CAP)?;
let sample = sample.write_from_fn(|i| (i % 251) as u8);  // 直接写进共享内存，不经栈/堆中转
sample.send()?;
```

订阅侧：

```rust
let subscriber = service.subscriber_builder().create()?;
if let Some(sample) = subscriber.receive()? {
    let len = sample.len();          // 变长由 iceoryx2 的 header 记录
    let bytes: &[u8] = &sample;      // Deref 到 [u8]
}
```

【实测】发布侧 `loan + write(4 MiB) + send` 共 **149 ms**（debug 构建，逐字节 `write_from_fn`，未优化）；订阅侧读到 4 MiB 并做逐字节校验共 **826 ms**（debug 构建，**绝大部分时间花在 PoC 自己的校验循环上**）。

⚠️ **这两个数字不是性能结论**——它们是 debug 构建 + 含自写校验的结果。真正的性能参考见 §5.5 的官方数据。

**与现状对比**：现有 `plugin_socket` / `plugin.rs` 里发一帧是

```rust
let text = serde_json::to_string(&request)?;
socket.send(Message::text(text)).await?;
```

路线 B 是 `serde_json::to_vec(&request)` → `loan_slice_uninit(len)` → `write_from_slice` → `send`。
**行数相当，甚至更少**（没有 async/await、没有 WebSocket 帧、没有升级握手）。所以"大量数据的代码复杂度"这个问题，答案是：**传输层不复杂，复杂的是内容之外的那几件配置与生命周期的事**。

### 5.3 三个真实会咬人的坑（都实测过）

**坑 1：不配 `initial_max_slice_len`，大切片直接租不到。**
【实测】把 4 MiB 的 `loan_slice_uninit` 用在默认配置的 publisher 上：

```
BIG-PUB-DEFAULT loan_error=ExceedsMaxLoanSize
```

官方对该错误的说明是："The provided slice size exceeds the configured max slice size. To send data with this size a new port has to be created with a larger slice size or the port must be configured with an `AllocationStrategy`."

⇒ **默认没有动态增长**。想要"随便多大都能发"，必须显式配 `AllocationStrategy::PowerOfTwo` 或 `BestFit` 并给个 `initial_max_slice_len` 提示。

**坑 2：动态扩容会丢样本。**
【官方】FAQ "Losing Dynamic Data"：如果用了 allocation strategy，发送方在扩容之后立刻退出，已经发出的样本可能丢失；建议用"上次发送的实际大小"当 `initial_max_slice_len`，或者干脆用 `Static`。
【实测】用 `initial_max_slice_len(8)` + `PowerOfTwo` 从 8 字节一路扩到 1.5 MiB，4 条不同长度的载荷全部送达（`lens=[32, 68, 196634, 1572890]`）；但那是"发送方活着"的场景。
【官方】动态分配还有重分配次数上限（`MAX_NUMBER_OF_REALLOCATIONS`），unreleased 分支还在修"最大重分配次数与段数"的问题。

**坑 3：`/dev/shm` 是 tmpfs，容量就是内存，且 Docker 默认只有 64 MB。**
【官方】Linux 下数据在 `/dev/shm`（tmpfs），不持久化、算 RAM；FAQ 明确："By default, a Docker container has a shared memory size of 64 MB... The shared memory size can be adjusted with the `--shm-size=` parameter"。另外还有 `ulimit -n`（文件描述符）与 `vm.max_map_count`（内存映射数）两个 OS 限制。
【官方】iceoryx2 **按最坏情况预分配**：每个 publisher 的数据段大小 = 载荷 × (订阅者数 × 缓冲深度 × 历史 …)。所以"4 MiB 载荷 × 16 缓冲 × 8 订阅者"这种配置会瞬间吃掉几百 MB。
【实测】跑完所有用例后 `/dev/shm` 只残留一个 16 字节的 `iox2_<hash>_node.0_9_3.global_mgmt`，说明正常退出时数据段会被回收，不会持续膨胀。

### 5.4 生命周期：异步代码的隐形陷阱

- `subscriber.receive()` 返回的 `Sample` **借用了共享内存**；持有它期间该槽位对 publisher 仍是"被占用"的。iceoryx2 用 `subscriber_max_borrowed_samples` / `subscriber_max_buffer_size` 限定上限，**持有过多样本会导致 `LoanError::ExceedsMaxLoans`（发送方租不到新样本）**。
- 【官方/推断】没有 async API，`receive()` 是非阻塞的。要在 tokio 里用，只有两条路：把端点固定在一个专用线程上轮询/`WaitSet`，或者用 `ipc_threadsafe::Service` 把端点搬进 `spawn_blocking` / 独立线程。
- **实践经验（推断但很确定）**：异步任务里拿到 `Sample` 后应当**尽快拷成 owned 数据再 `.await`**，不要让 `Sample` 跨越 `await` 边界。这跟"零拷贝"的初衷有张力，但收益（免掉 socket/内核拷贝）仍然存在。

### 5.5 官方性能数据（项目自测，非本机）

【官方】iceoryx2 仓库 `internal/plots/` 的机制对比数据（Intel i7-13700H / Linux 6.10 / rustc 1.81）：

| 载荷 | iceoryx2 | iceoryx(classic) | POSIX 消息队列 | Unix domain socket |
| :--- | ---: | ---: | ---: | ---: |
| 64 B | 0.098 µs | 1.1 µs | 1.1 µs | 1.6 µs |
| 16 KB | ~0.098 µs | 1.1 µs | 5.6 µs | 5.6 µs |
| 256 KB | ~0.098 µs | 1.1 µs | 63 µs | 70 µs |
| 1 MB | ~0.098 µs | 1.1 µs | 250 µs | 280 µs |
| 4 MB | 0.094 µs | 1.1 µs | 980 µs | 1100 µs |

架构对比（同/跨核延迟）：i7-13700H Linux 92 ns / 326 ns；Ryzen 7 7840S 109 ns / 222 ns；树莓派 4B 774 ns。

⇒ **这正是换共享内存的动机**：UDS 在 4 MB 时已经到 1.1 ms，而 iceoryx2 基本是常数。当前项目用 UDS + WebSocket + JSON，在大载荷上是要付这个账的。

### 5.6 自己仍要写的协议部分

iceoryx2 只提供"一次发送 = 一个样本"的语义，**流式语义仍然要自己写**。PoC 里 `TurnChunk` 就不得不带 `seq` / `total` / `turn_id` / `len` 四个字段——这跟现有 `wire.rs` 里靠 turn 状态机维持顺序是同一件事，只是换了个地方写。

不过 request-response 有一个意外之喜【官方】：**一个请求可以对应多条响应**（`ActiveRequest::loan_uninit()` 可以在循环里发多条），这天然匹配"LLM 流式输出"——比现在"WebSocket 双向 + 自己维护 turn 状态"更贴合。

### 6.1 现有通信面盘点（删什么、留什么）

### 6.2 逻辑链条 A：为什么现有 serde 类型**不可能**直接上共享内存

```
① 现有载荷全是 serde 类型（wire.rs / protocol.rs）
   └─ 字段里大量出现 String / Vec<String> / serde_json::Value / Option<T>
② iceoryx2 要求载荷实现 ZeroCopySend
   └─ 而 ZeroCopySend 要求：无堆指针、无 Drop、#[repr(C)]
③ 于是 String / Vec / Value / Option 全部在编译期被拒
   （实测：E0277；Option 是 0.9.0 起故意移除的）
④ 结论：不存在"把 wire.rs 的类型直接搬过去"这条路
   └─ 必须二选一：
      (a) 把类型重写成定长 POD（放弃 Value/动态长度）
      (b) 保留 serde 类型，但序列化成字节，用 [u8] 切片传
```

**这条链是整份研究的枢纽**：它说明"换 IPC 机制"实际上是"换数据表示"，工作量的大头在这里，不在 iceoryx2 的 API 上。

### 6.3 逻辑链条 B：`PluginEvent::Raw` 的"原样透传 rig JSON"锁死了路线

```
① 现有设计（dev-notes.md §2.2/§2.3）刻意让 kb_core **不理解** rig 的数据，
   插件把 rig 的原始 JSON 原样上报，转换由 kb_rig_llm_v1_adapt 在服务端进程内做。
② 这条设计的载体是 serde_json::Value —— 一个"任意形状的 JSON"。
③ 任意形状 与 定长 POD 在语义上互斥（POD 必须编译期确定布局）。
④ 所以只要保留"原样透传"这条设计，载荷就**只能**是变长字节（路线 B）。
⑤ 反过来说：若坚持路线 A（全 typed 零拷贝），就必须重新定义
   "插件上报什么" —— 即把 rig 的语义在插件侧就翻译成 abs_llm::v1 的定长类型，
   这与 §2.2"转换发生在 kb_core 进程内"的设计决策直接冲突。
```

⇒ **这是一个需要团队重新拍板的设计冲突**，不是纯技术选择。两条出路：

- 保留 §2.2/§2.3，走路线 B（或 C 中"内容帧走 B"）——改动小，但放弃内容帧的 typed 零拷贝。
- 推翻 §2.2/§2.3，把适配下沉到插件侧——能拿到路线 A，但要重写 `kb_rig_llm_v1_adapt` 的接入位置，且 `kb_core` 从此需要理解更多语义。

### 6.4 逻辑链条 C：删掉 HTTP 之后，`kb_svc_salvo` 的另一半去哪

```
① kb_svc_salvo 现在其实是两个东西的混合物：
   (a) HTTP/Web 服务（server/web/web_ws/plugin/assets）
   (b) 会话中枢与业务逻辑（hub/wire/settings）
② "全面删除 HTTP" 删掉的是 (a)。
③ 但 (a) 是 (b) 当前的唯一宿主：kb_svc_salvo::launch 把两者串起来，
   而 kb_core/src/main.rs **只做三件事**（解析参数、初始化日志、调 launch）。
④ 于是 (b) 必须重新找宿主。可选：
    - 上移到 kb_core（它本来就是"主进程"）
    - 留在某个新的服务库（例如 kb_svc_iceoryx2 的上一层）
    - 拆成 kb_svc_core（业务）+ kb_svc_iceoryx2（传输）
⑤ 若选"上移到 kb_core"，则 kb_core 从 200 余行的入口壳
   变成真正的业务进程；这是一个**比换 IPC 更大**的结构调整。
```

⇒ 建议：**新增一个业务库**（暂名 `kb_svc_core` 或直接让 `kb_core` 承担），把 `hub` / `settings` / `wire` 的语义搬过去，`kb_svc_iceoryx2` 只做传输绑定。这样"传输可替换"这件事才真正成立——否则业务逻辑会和 iceoryx2 的类型粘在一起。

### 6.5 逻辑链条 D：tokio 多线程运行时**必须**用 `ipc_threadsafe::Service`

这是本次实测里最"值钱"的一条，因为它会直接决定 `kb_core` 的代码结构：

```
① kb_core 目前是 #[tokio::main] 多线程运行时（tokio 特性含 rt-multi-thread）。
② iceoryx2 有两套 Service：`ipc`（默认）与 `ipc_threadsafe`。
③ 实测：`ipc::Service` 的端点**不是 Send**
   - 把 Subscriber 移进 std::thread：
     error[E0277]: `Rc<...SubscriberSharedState<ipc::Service>>` cannot be sent between threads safely
   - 显式断言 Send：
     Publisher / Subscriber 双双 E0277（内部是 Rc，不是 Arc）
④ ⇒ 用默认 `ipc::Service` 时，端点只能活在一个线程里；
   要在 tokio::spawn / spawn_blocking 之间传递，必须用 `ipc_threadsafe::Service`。
⑤ 实测：`ipc_threadsafe::Service` 的端点满足 Send + Sync，
   可以正常丢进 std::thread 并收到数据（THREADSAFE-DONE received 42）。
⑥ ⇒ 结论：**kb_core 侧统一用 `ipc_threadsafe::Service`**，
   并且这个选择必须写进 `abs_kb_svc` 的抽象约定里（否则各插件各选一套，
   同名服务的 Service 变体不一致会直接连不上）。
```

### 6.6 逻辑链条 E：socket 路径 → 服务名，以及"well-known 地址"的缺口

```
① 现有机制：kb_core 生成 `<runtime_dir>/kb-<date>-<uuid>.sock`，
   通过 `--socket <path>` 与 `LLM_KB_PLUGIN_SOCKET` 环境变量**主动告诉**子进程。
   插件不需要"找"服务，路径是父进程喂的。
② iceoryx2 没有用户可见的路径，只有 ServiceName（官方约束：非空、
   不得以 "iox2://" 开头、最长 255 字符；内部会哈希成文件名）。
   ⇒ "把路径喂给子进程"这一步可以原样保留，只是内容从路径变成服务名。
③ 但**桌面客户端不是 kb_core 拉起的**，没人喂它名字。
   今天这个缺口是靠"固定端口 127.0.0.1:8788"补上的。
   换成共享内存后，固定端口不存在了，必须补一个新的 well-known 机制：
   - 方案 α：固定服务名（例如 `llm_kb/admin`）——最简单，但多实例会撞车
   - 方案 β：`global.prefix` 配置项给整个 iceoryx2 域加前缀（官方配置项，
     实测源码里 `Global { root_path, prefix, service, node, creation_timeout }`），
     每个 kb 实例一个前缀
   - 方案 γ：用 `ipc::Service::list(...)` 做服务发现 + 一个锁/状态文件记录当前实例
④ 另外还有**残留与并发**问题：现有设计刻意用"日期+UUID"避免历史 socket 冲突；
   iceoryx2 侧 `/tmp/iceoryx2/{nodes,services}` 与 `/dev/shm/iox2_*_node...global_mgmt`
   会残留（实测），但 0.9.0 专门做了一版"去中心化崩溃恢复"
   （lock-free robust unique index set），实测 SIGKILL 掉发布者后再次通信正常。
```

### 6.7 逻辑链条 F：安全模型（API key 会走过这条通道）

```
① 现状：`PluginRequest::Ask` 携带完整的 `LlmServiceConfig`，**含明文 API key**；
   它经由 127.0.0.1 TCP 或 0600 的 UDS 传给插件。
② iceoryx2 的安全边界【官方 FAQ】：
   "iceoryx2 does not yet implement access rights management for services and
    therefore only the user, under which the process runs, can access the underlying
    resources. Processes started under a different user will receive an insufficient
    permissions error when opening them."
   即：**边界是 OS 用户，不是服务**。
③ ⇒ 同一 OS 用户下的任何进程，只要知道服务名，就能读写该服务的载荷
   （服务名还可被 `Service::list` 枚举）。没有任何 per-service 凭据。
④ 对比现状：
   - 相对 TCP(127.0.0.1)：**更安全**（同机其他用户被挡住，现在挡不住）
   - 相对 UDS(0600)：**基本持平**
   ⇒ 所以这不是"引入 iceoryx2 带来的新增风险"，而是"原本就存在的模型被继承"。
⑤ 但要注意两个放大器：
   - `dev_permissions` feature（**默认关闭**）会把所有资源设成 rwx 给所有人，
     官方明说"shall not be used in production"，只给 Docker 场景救急。
   - 官方 roadmap 里 "Identity and Access Management" 仍是**未勾选**项。
⑥ ⇒ 建议（推断）：短期沿用现状（同用户信任模型），但把"API key 明文过 IPC"
   列为显式技术债；若要收紧，应在应用层做（每实例密钥 / OS keychain /
   payload 加密），不要指望 iceoryx2 提供。
```

### 6.8 逻辑链条 G：`abs_kb_svc` 的抽象与 `ZeroCopySend` 的依赖泄漏

需求给的模块分工是：`abs_kb_svc` 必选、`kb_svc_iceoryx2` 可选。这条分工与 iceoryx2 的类型系统有一个**结构性张力**：

```
① 若 `abs_kb_svc` 里的载荷类型要实现 `ZeroCopySend`
   （无论是 derive 还是手写 unsafe impl），
   它就必须依赖 `iceoryx2-bb-derive-macros` / `iceoryx2-bb-elementary-traits`。
   ⇒ "可选依赖"名存实亡：只要用载荷类型，就必然拉进 iceoryx2 的生态。
② 若 `abs_kb_svc` 只定义**与传输无关的语义类型**（纯 Rust、可 serde），
   而把 `ZeroCopySend` 版本的载荷类型放到 `kb_svc_iceoryx2`，
   则插件端为了发一条消息必须同时依赖两个 crate。
   ⇒ 但 `kb_svc_iceoryx2` 仍然是"可选"的：不用共享内存的插件可以不依赖它。
③ 还有第三条路：`abs_kb_svc` 只定义**面向字节的通道抽象**
   （`trait Publisher { fn send_bytes(&self, &[u8]) -> Result<..>; }`
   + `trait Subscriber`），语义类型用 serde 表达。
   这样 `abs_kb_svc` 零 iceoryx2 依赖，`kb_svc_iceoryx2` 提供实现。
   ⇒ 代价：彻底放弃 typed 零拷贝（等于把 §5.1 的路线 B 定为唯一路线）。
```

三种方案对应三种"抽象层厚度"，必须选一个；**不能既要 `abs_kb_svc` 零 iceoryx2 依赖、又要 typed 零拷贝载荷**。

### 6.9 逻辑链条 H：为什么现在改，成本最低

```
① kb_svc_salvo::launch 里明确留着 TODO（阶段 4）：
   "在此处启动 kb_rig_llm 子进程，并把 socket 路径传给子进程。"
   ⇒ **插件进程监管（PluginSupervisor）还没写**，现在改没有迁移成本。
② kb_admin_desktop 目前**没有接任何传输层**：Dart 侧只有本地内存 store，
   对话面板上写着"对话通道尚未接入"。
   ⇒ 客户端侧也没有迁移成本。
③ abs_kb_svc 目前是**空 crate**（lib.rs 只有一行空白）。
   ⇒ 抽象层是白纸，正好按新方案设计。
④ 三条加起来：**这次重构几乎没有"存量代码要搬"的负担**，
   只有"设计要重做"的负担。等到子进程监管、客户端传输、抽象层都落地之后再改，
   成本会高一个数量级。
```

## 7. 模块分工的可行性评估

需求给的三个模块，逐个评估：

### 7.1 `abs_kb_svc`（必选，定义语义 + 通道抽象）

- **定位成立**，且 §6.9 ③ 说明现在是设计它的最佳时机。
- **必须先定的三件事**（见 §9 决策 2/3/4）：
  1. 载荷是 typed 定长还是字节（决定要不要依赖 iceoryx2）；
  2. 抽象是"通道 trait"还是"共享内存专用类型"；
  3. Service 变体统一为 `ipc_threadsafe`。
- ⚠️ **注意已有依赖**：`abs_kb_svc/Cargo.toml` 目前已经依赖 `buffex` 与 `mm_ptr`【实测读码】。这两个是团队自研的缓冲区/内存映射抽象，语义上和 iceoryx2 的共享内存**高度重叠**。引入 iceoryx2 之前需要明确：是替换、是并存、还是 `buffex`/`mm_ptr` 退居"ic 内部实现"的角色。这是本次研究没有覆盖、但必须回答的问题。

### 7.2 `kb_svc_iceoryx2`（新增，iceoryx2 的具体落地）

- **定位成立**，而且**强烈建议就按这个边界收敛**：§2.3 说明 0.9.x 每个 minor 都有 breaking change，把 iceoryx2 关在一个 crate 里，升级只影响一层。
- 需要包含的职责：
  - `Node` 生命周期与 `Config`（含 `global.prefix` 实例隔离）的建立；
  - 服务的创建/打开、QoS（`max_publishers` / `max_subscribers` / `history_size` / `subscriber_max_buffer_size` / `initial_max_slice_len` / `AllocationStrategy`）的集中配置；
  - **服务名生成/解析**（取代 `plugin_socket`，见 §6.6）；
  - `ipc_threadsafe::Service` 与 tokio 的桥接（专用线程 + 轮询/`WaitSet`，见 §5.4）；
  - 从"通用语义帧"到"共享内存载荷"的编解码（路线 B 的 serde↔字节，或路线 A 的转换）。
- ⚠️ **必须锁死版本**：`iceoryx2` 与可能用到的 `iceoryx2-bb-container` 必须 `=0.9.3` 精确锁定（§4.5 的 IncompatibleTypes 陷阱）。

### 7.3 `kb_plugins/*` 与 `kb_admin_desktop`（必选 `abs_kb_svc` + 可选 `kb_svc_iceoryx2`）

- 插件侧：作为 request-response 的 **server** 或 pub/sub 的一方，形态成立；`kb_rig_llm_v1_agent` 现在只有 `protocol.rs`（218 行）与 13 行的 `lib.rs`（模块文档 + `pub mod protocol;`），改动面很小。
- 桌面客户端侧：Flutter 的 Rust 侧（`kb_clients/kb_admin_desktop/rust`）目前是独立 workspace、只依赖 `flutter_rust_bridge`。把 `abs_kb_svc` + `kb_svc_iceoryx2` 加进去**技术上可行**，但要注意：
  - 该 crate 是 `cdylib`/`staticlib`，被 Flutter 各平台构建链（Cargokit）驱动；加依赖会显著增加各平台构建时间；
  - iOS/Android 目标会直接失败（§3.2）；
  - 【官方】跨平台共享内存**要求两端用同一个类型定义**（§4.4），所以 `abs_kb_svc` 必须能在移动端/桌面端都编译——如果它依赖了 iceoryx2（std），移动端目标会在编译期就炸，这反而是"早点失败"的好事。

### 10.3 实测结果汇总

| 用例 | 结果 |
| :--- | :--- |
| 跨进程 pub/sub，100 条定长结构体（含中文 UTF-8） | ✅ `received=100 last_seq=99`，文本完整 |
| 跨进程 request/response（含中文请求与回显） | ✅ `status=0 body="echo:你好，请介绍一下知识库"` |
| 4 MiB 单次切片载荷（`initial_max_slice_len` + `PowerOfTwo`） | ✅ `len=4194304`，校验通过 |
| 4 MiB + `AllocationStrategy::Static` | ✅ 同上 |
| 4 MiB **不配** `initial_max_slice_len` | ❌ `loan_error=ExceedsMaxLoanSize`（**预期失败，用于确认失败模式**） |
| 变长载荷（32 B / 68 B / 192 KiB / 1.5 MiB，`PowerOfTwo` 从 8 B 扩容） | ✅ `lens=[32, 68, 196634, 1572890]` |
| 同服务二次启动（进程全部退出后重跑） | ✅ 正常 |
| SIGKILL 发布者后再通信 | ✅ 正常（0.9.0 的去中心化崩溃恢复生效） |
| `ipc_threadsafe::Service` 端点跨线程 | ✅ `THREADSAFE-DONE received 42` |
| `String` / `Vec<u8>` / 含 `String` 的 `#[repr(C)]` / `Option<u64>` 作为载荷 | ❌ 编译期 E0277（**预期失败**） |
| `#[repr(C)] enum`（含带字段变体）作为载荷 | ✅ 编译通过（正向发现） |
| 默认 `ipc::Service` 端点要求 `Send` | ❌ E0277，内部是 `Rc<...SharedState<ipc::Service>>`（**预期失败**） |
| 依赖规模（dev 构建，`cargo tree` 去重） | 87 个 crate，169 行 |
| 退出后残留 | `/dev/shm/iox2_<hash>_node.0_9_3.global_mgmt`（16 B）；`/tmp/iceoryx2/{nodes,services}` 空目录 |
